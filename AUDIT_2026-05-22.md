### 1.1 [VÉRIFIÉ] `src/inpi.py:274` — `FL` mappé à `ventes_marchandises` : FL **n'existe pas** dans les bilansSaisis INPI

Le formulaire CERFA 2052 expose **FA / FB / FC** pour les ventes de marchandises (France / Export / Total). FL = "Chiffres d'affaires nets total" (3ᵉ colonne du sous-tableau FJ/FK/FL).

Mais dans les données INPI réelles, **les codes "colonne France" et "colonne Export" ne sont jamais présents** : seul le code "ligne" est exposé, avec les colonnes France/Export/Total via les champs m1/m2/m3 :
- `FA m3 = Ventes marchandises TOTAL N`
- `FG m3 = Production services TOTAL N`
- `FJ m3 = CA NET TOTAL N` ← **vrai CA**
- `FR m3 = Total produits exploitation N` ← ce que le code extrait actuellement

Test sur ENERFLUID 2023 : 5 bilans saisis ont les codes page-3 = `['FA','FG','FJ','FP','FQ','FR','FS','FT','FU','FW','FX','FY','FZ','GA','GC','GE','GF','GG','GO','GP','GR','GU','GV','GW']` — **FL et FK absents partout** (vérifié sur 5 cibles retenues).

**Impact** : `LIASSE_NORMAL_CODES["FL"] = "ventes_marchandises"` et `["FK"] = "production_vendue_services"` extraient toujours `None`. La fonction `compute_ratios` retombe en fallback sur `production_exercice = FR`, qui surestime le CA.

Cas réels comparant FR vs FJ (différence = subventions + reprises + autres produits) :

| SIREN | Notre CA (FR m3) | Vrai CA (FJ m3) | Δ |
|---|---|---|---|
| 612019505 ENERFLUID | 5 170 496 | 5 082 216 | +88 280 |
| 722064565 PRAMAC | 4 087 977 | 4 064 226 | +23 751 |
| 332444322 PPF | 2 723 158 | 2 678 016 | +45 142 |
| 692051394 TECHNICAIR | 4 200 914 | 4 119 021 | +81 893 |
| 631720190 SOMEPLAS | 3 025 720 | 3 040 026 | -14 306 |

Source officielle : CERFA 2052-SD 2025 (`https://www.impots.gouv.fr/sites/default/files/formulaires/2050-liasse/2025/2050-liasse_5013.pdf`).

**Correction suggérée** : remplacer le couple `("FL","FK")` par `("FJ", 3)` et reconstituer un champ `ca_net_total` = FJ.m3.

### 1.2 [VÉRIFIÉ] `src/inpi.py:283` — `FW` mappé à `subventions_exploitation` (devrait être `FO`)

Sur le 2052 officiel :
- **FO = Subventions d'exploitation**
- **FW = Autres achats et charges externes**

Ces deux libellés sont diamétralement opposés (un produit vs une charge). Le mapping actuel inverse les deux. Pour ENERFLUID 2023, le champ `subventions_exploitation` extrait par le code vaut 955 935 € — mais c'est en fait FW (Autres achats et charges externes). Pas d'impact sur `compute_ratios` car ni FO ni FW ne sont utilisés dans le calcul de l'EBE actuel. Mais le code `extract_bilan` retourne une donnée fausse via `bilan["subventions_exploitation"]`.

### 1.3 [VÉRIFIÉ] `src/inpi.py:278` — `FS` mappé à `consommations_externes` (devrait être `achats_marchandises`)

Sur le 2052 officiel :
- **FS = Achats de marchandises** (y c. droits de douane)
- **FW = Autres achats et charges externes**

Le code dit que `FS = "consommations_externes"`. C'est une approximation au mieux ; en toute rigueur les "consommations externes" PCG = FS + FT (variation stock marchandises) + FU (achats MP) + FV (variation stock MP) + FW (autres achats). FS seul ne reflète qu'une partie.

### 1.4 [VÉRIFIÉ] `src/inpi.py:267-272` — codes BV / BX du 2050 (Bilan Actif) sont mal mappés

Sur le 2050 officiel (CERFA 2050-SD 2025) :
- **BV = Avances et acomptes versés sur commandes** (codé `creances_clients_brut` — FAUX)
- **BX = Clients et comptes rattachés** (codé `autres_creances` — FAUX, c'est en fait les clients)
- **BZ = Autres créances** (non codé — donc créances non extraites correctement)
- **CD = VMP** ✓
- **CF = Disponibilités** ✓
- **CO = TOTAL GÉNÉRAL** ✓

**Impact** : les libellés affichés dans le classeur Excel `screening_echantillon_3.xlsx` sont trompeurs (la valeur affichée comme "créances clients brut" est en réalité les avances et acomptes).

### 1.5 [VÉRIFIÉ] `src/inpi.py:266-272` — code DI / EA / DX du 2051 (Bilan Passif) mal mappés

Sur le 2051 officiel :
- **DI = Résultat de l'exercice** (non codé du tout)
- **DL = TOTAL (I) capitaux propres** ✓ (codé correctement)
- **DX = Dettes fournisseurs et comptes rattachés** (non codé)
- **EA = Autres dettes** (codé `dettes_fournisseurs` — FAUX, c'est DX qui est le vrai code)

Pour ENERFLUID 2023 :

Donc le champ `dettes_fournisseurs` retourné par `extract_bilan` est numériquement éloigné d'un facteur 10-15. Pas d'impact direct sur les ratios (non utilisé par `compute_ratios`) mais affiché dans l'Excel produit par `generate_comptes_excel_bytes`.

### 1.7 [VÉRIFIÉ] `src/inpi.py:400` — formule autonomie financière fausse

```python
autonomie = (cp / (cp + (emprunts or 0))) if cp and (cp + (emprunts or 0)) > 0 else None
```

La définition standard (analyse-financiere skill, Vernimmen, Banque de France) :
> Autonomie financière = **Capitaux propres / Total bilan (passif)**.

Le code calcule `CP / (CP + emprunts)` ce qui équivaut à la part des CP **dans la dette financière** seulement, ignorant dettes d'exploitation (fournisseurs, fiscales/sociales) et autres passifs.

Pour ENERFLUID 2023 :
- CP = 5 099 976 ; Total passif EE = 6 046 558
- Vraie autonomie = 5 099 976 / 6 046 558 = **0,843** (cohérent avec societe.com qui affiche 84,3 %)
- Notre code calcule 5 099 976 / (5 099 976 + 0) = **1,000** ❌

Pour TECHNICAIR : autonomie = 1,000 alors qu'elle devrait être ~6 141 841 / 6 636 195 = 0,925.

**Correction suggérée** :
```python
total_passif = bilan.get("total_passif")
autonomie = (cp / total_passif) if cp and total_passif and total_passif > 0 else None
```

### 1.9 [VÉRIFIÉ] `src/inpi.py:391` — EBE proxy incomplet (sans provisions)

```python
ebe = (rex + dap) if rex is not None else None
```

Avec `dap = bilan.get("dap_exploitation") = GA` (Dotations aux amortissements **uniquement**).

L'EBE proxy (REX + DAP) devrait inclure **GA + GB + GC + GD** : dotations aux amortissements + dotations aux provisions sur immo + sur actif circulant + pour risques et charges.

Pour ENERFLUID 2023 :
- GA = 2 549 (amortissements), GC = 99 885 (provisions actif circulant)
- EBE codé = REX (561 284) + GA (2 549) = **563 833**
- EBE corrigé = REX + GA + GC = **663 718** (+18 %)

Pour des entreprises ayant des provisions élevées (clients douteux, stocks) l'écart peut être > 20 % du proxy.

Plus rigoureusement, le PCG définit :
> EBE = VA + Subventions d'exploitation - Impôts/taxes - Charges de personnel
> = REX + DAP totales + Dotations provisions - Reprises sur amort/prov (FP) - Autres charges (GE) + Autres produits (FQ)

La forme la plus juste serait :
```python
dap_total = sum(filter(None, [bilan.get("dap_amort"), bilan.get("dot_prov_immo"),
                              bilan.get("dot_prov_ac"), bilan.get("dot_prov_rc")]))
reprises  = bilan.get("reprises_amort_transferts") or 0
ebe = rex + dap_total - reprises - (bilan.get("autres_charges_gE") or 0) + ...
```

Mais l'approximation usuelle adoptée dans la place financière est :
> **EBE ≈ Excédent brut d'exploitation = REX + DAP exploitation totales (GA+GB+GC+GD) − Reprises (FP)**.

Le code actuel est donc **sous-évalué** sur la composante DAP+provisions et **n'enlève pas les reprises**.

## 3. Améliorations recommandées (non bloquantes)

### 3.1 `src/inpi.py:519` — calcul d'âge ignore le jour de naissance

```python
age = today.year - annee - (1 if today.month < mois else 0)
```

Cette formule ne tient pas compte du jour. Pour un dirigeant né le 1965-07-15 et un screening du 2026-07-10, le code donne 61 ans mais l'âge réel est 60. Impact négligeable (1 mois de marge sur l'année). Si les dates INPI passent un jour à inclure le `JJ`, le bug deviendra latent.

**Correction simple** :
```python
from datetime import date
try:
    annee = int(dn[:4])
    mois = int(dn[5:7]) if len(dn) >= 7 else 6  # défaut milieu d'année
    jour = int(dn[8:10]) if len(dn) >= 10 else 15
    birth = date(annee, mois, jour)
    age = (today - birth).days // 365  # approximation
except (ValueError, IndexError):
    continue
```

## 7. Conclusion synthétique

**Le pipeline produit des chiffres globalement plausibles mais structurellement faux sur 3 points** :
1. Le **CA** extrait depuis `production_exercice` (FR) au lieu de `chiffres d'affaires nets` (FJ) — surestimation systématique de 1 à 3 %.
2. L'**autonomie financière** = CP / (CP + emprunts) au lieu de CP / Total bilan — ratio à 100 % pour les entreprises sans dette, alors qu'il devrait être ~80-90 %.
3. La **marge EBE** dans l'Excel produit par `enrich_sprint3.py` n'est pas formatée en pourcentage — lue à 0,11 par l'utilisateur au lieu de 10,9 %.

**Le mapping du régime simplifié `LIASSE_SIMPLIFIE_CODES` est quasi-entièrement faux** (page et libellés). Aucun impact sur la run actuelle (0 cible en régime S sur les 5 retenues) mais c'est une bombe à retardement pour les screening futurs sur des NAF dominés par les TPE.

**Le mapping des codes `roleEntreprise` est empirique, non sourcé**. Sur les 5 cibles retenues, 2 sont dirigées par un personnage en code 30 (`Associé indéfiniment responsable` selon le code), or ces 2 entreprises sont des **SARL** où ce statut ne devrait pas exister. À investiguer auprès de l'INPI ou via un cas test (modifier temporairement le code 30 en "non-direction" et voir combien de cibles changent de catégorie).

**Le test HURSIN passe** avec le mapping actuel, mais pour de mauvaises raisons : il s'appuie sur la classification du code 70 en "direction", qui n'est pas confirmée par une source officielle.

Le code Streamlit (`app.py`) est globalement propre, sans bug visuel détecté lors de la relecture, et cohérent avec la doctrine `dashboard-finance`.
